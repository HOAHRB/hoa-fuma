## 是否只影响首几个请求

本地完整生产包测量：同一 2023 年级 URL 首次 TTFB 约 146 秒，重复访问约 54 毫秒；都是源站直接请求，最终返回 200。这证明热缓存帮助很大，也说明超过 Worker 的 29 秒时限不能直接等同于源站自身抛出 500。

但不能保证“失败几次后永久稳定”：

- 新 URL 首次访问仍需生成页面；新年级/专业可能触发尚未初始化的目录缓存。
- 当前部署工作流先 `docker rm -f`，再 `docker run`，没有挂载 Next 页面缓存卷。新容器失去此前运行时页面缓存和进程内缓存。
- 单纯重启 Node 进程会失去内存 Map；同一容器的磁盘缓存可能保留，应与重建容器区分。
- 页面缓存到期需要再生成；同一进程的 SEO/目录 Map 不会仅因页面一小时 TTL 自动清空，所以不能说每小时必定重复全站扫描。
- 同步文件扫描阻塞 Node 事件循环，冷启动并发请求也可能等待。客户端超时后，源站计算可能继续并帮助后续请求，但尚未验证取消行为，不能以此作稳定性保证。

## 隔离研究方案的代价

研究分支 `codex/cold-start-investigation` 位于 `D:/dev/HOAHRB/hoa-fuma-cold-start`。当前未提交、未部署。

实验方案将 SEO、路径、目录、课程列表索引在 `pnpm build` 生成；现有流程由 Actions 中的 Docker 镜像构建执行，不在容器启动时生成。年级页只传递专业入口，减少全年级课程树序列化。

当前索引新增 32,804,573 字节（32.8 MB），此前没有这套预生成索引，新增量是从 0 到 32.8 MB；不能据此声称整个旧镜像只有 0 或 125.8 MB。索引约为当前正文大小的 26%，镜像整体前后大小尚未测量。分片缓存已限制为最近 64 项、按序列化大小合计不超过 16 MiB；解析后对象的实际堆内存可能更大，路径等模块也会持有自己的固定数据，因此这不是整个进程的内存上限。树数据仍有重复，正式部署需要记录镜像大小和冷请求期间的容器内存。

完整前后性能与验证范围见 `docs-index-performance.md`。优化样本首次年级页约 6 秒，仅是 Windows 本机单轮测量；没有生产服务器、并发及内存峰值证据，不能保证线上一定低于 29 秒。
